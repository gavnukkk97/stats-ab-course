# Проектирование АБ-платформы

## Чек-лист проектировщика (короткая версия)

**Сплит**
- хэш: детерминизм + равномерность + лавинность (MD5/SpookyHash ок, FNV — нет)
- домены → слои → 1000 бакетов: `bucket = hash(user_id + соль_слоя) % 1000` (Google KDD'10)
- слои = независимые лотереи → десятки параллельных тестов; ёмкость слоя планируй
- sticky assignment: миграция ключа (cookie→аккаунт) — только через sticky-мост, иначе при независимом новом хэше около половины пользователей с новым ключом меняют группу

**Данные**
- exposure = первый контакт юзера с вариантом (честный timestamp, не лог-время)
- дедуп (user, experiment) обязателен — дубли ретраев дают SRM
- озеро: Parquet, партиции дата×эксперимент; юнит-таблица для анализа
- вычисления: ночной батч; **бакетизация** юзеров → 100–1000 агрегатных строк (×100 по строкам, точность зависит от агрегата: n/sum/sumsq сохраняет среднюю и Welch, bucket means требуют калибровки) — так тянут сотни млн p-value/день (Авито)
- метрик-хаб: единые определения метрик с владельцами и аудитом

**Процессы**
- заявка = дизайн-док (MDE→n автоподсчёт, метрики из хаба, guardrails)
- гейты: SRM (χ², порог 0.001), инварианты, авто-стоп по guardrails (mSPRT) — нельзя обойти
- лента результатов: эксперименты как контент (KB, пульс-дайджесты)

**Календарь гипотез** (ниша — вендоры не делают)
- очередь с приоритетом = ценность/(слот×время), а не FIFO и не только RICE
- календарь = слои×недели; система предлагает ближайший свободный слот под MDE
- velocity-метрики: время идея→решение, доля ожидания в очереди, throughput
- ёмкость: прогноз тестов/квартал из трафика и средних MDE; buy vs build (вендор за недели vs своя под свои данные)

## Обязательные контракты

- Доменная eligibility и arm allocation — независимые хэши; расширение enrollment не должно менять arm уже включённых. Снимок включает домены, соли, доли, число бакетов и версии.
- ITT строится по assignment eligible-популяции, а не автоматически по exposure. Сохраняйте нули и проверяйте зрелость окна каждого участника.
- Для равных рук N_total≈31,4(CV/MDE_rel)² при 95%/80%; n_arm=N_total/2. Не путайте эти размеры.
- Принятие заявки резервирует слот; отказ не меняет состояние. Повторная заявка идемпотентна или явно отклоняется; завершение освобождает ресурс. Общие изменяемые настройки не должны протекать между экземплярами.
- Инварианты определены до treatment; продуктовое изменение событий — не автоматическая поломка. Любой неразрешённый validity stop блокирует финальный SHIP.
- Мониторинг: budget по K запланированным взглядам и guardrails или валидная sequential-процедура. Фиксированный z сам по себе не mSPRT. Безопасность и отсутствие обнаруженного вреда — разные статусы.
- Перед buy/build проверьте актуальный продукт, тариф и дату. Готовые Jira-интеграции существуют (Optimizely); отсутствие функции в одном обзоре не доказывает её отсутствие на рынке.
