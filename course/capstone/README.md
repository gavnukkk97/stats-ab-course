# Итоговый проект: рекомендации в корзине

В «ЕдаДома» тестируют новый блок рекомендаций. Назначение сделано по аккаунту среди заранее eligible-пользователей; вариант сохраняется 14 дней. Владелец хочет решить, раскатывать ли функцию.

**До просмотра результатов** заполните [протокол](../exercises/protocol-template.md). OEC — маржа заказов на назначенного пользователя за 14 дней. Минимально полезный прирост +150 копеек на пользователя; допустимый рост доли пользователей с отменой +0,5 п.п. Плановый уровень 5%, двусторонняя проверка OEC; безопасность — односторонняя граница. Здесь только один guardrail. Вторичные метрики — диагностические, не заменяют OEC.

В `data/` лежат синтетические сырые выгрузки. Данные могут содержать технические повторы и требуют проверки; не считайте каждую строку независимым пользователем. В этом задании все 14-дневные окна уже завершены. До теста доступна маржа за такой же период, её можно использовать для планирования и заранее заданного adjustment.

| Файл | Поля и смысл |
|---|---|
| assignments.csv | user_id, variant (A/B), assigned_day, pre_margin_kopecks; одна назначенная eligible-популяция |
| exposures.csv | exposure_id, user_id, variant, day; фактический контакт; повторная доставка лога возможна |
| events.csv | event_id, user_id, day, margin_kopecks, cancelled; событие заказа, отмена имеет маржу 0 |

## Что сдать

1. Дизайн-док до анализа. Рассчитайте, какой размер выборки нужен для бизнес-порога при power=80%, и фактическую чувствительность доступного дизайна. Здесь планирование мощности означает обнаружение эффекта такого размера против нуля; 80% power не обещают 80% вероятности, что нижняя граница CI превысит сам бизнес-порог. Не используйте наблюдаемый эффект для observed power.
2. Отчёт о данных: уникальность ключей, окна, пропуски связей, стабильность назначения, SRM по исходной популяции и диагностика exposure. Объясните, что означает каждый сигнал.
3. Пользовательскую таблицу с нулями для отсутствующих заказов. Отдельно опишите деньги, конверсию и ratio; не меняйте estimand ради значимости.
4. Оценку OEC, CI, p-value и проверку guardrail. Если используете pre-данные, покажите метод и условия корректности.
5. Одностраничное решение roll/hold/rollback: полезность, неопределённость, безопасность, ограничения, следующий шаг. Ответ «недостаточно данных» допустим, если обоснован.
6. Воспроизводимый код, версии зависимостей и журнал очистки. Пользовательская версия — [student.py](student.py).

## Критерии оценки — 20 баллов

- Популяция, estimand, единица назначения/анализа и протокол — 4.
- Диагностика данных и обоснованная очистка — 4.
- Расчёты, uncertainty и проверка предположений — 5.
- Guardrail и бизнес-решение без подмены отсутствия значимости отсутствием эффекта — 4.
- Воспроизводимость и ясный отчёт — 3.

Критические ошибки: выбросить некупивших из OEC, фильтровать по нажатию новой кнопки, считать заказы независимыми юнитами, принимать p>0,05 за доказательство безопасности, менять анализ после просмотра ради нужного результата. При них проект возвращается на доработку независимо от баллов.

После самостоятельной сдачи откройте [разбор для преподавателя](solutions/README.md). Не смотрите генератор до анализа: он раскрывает заложенные механизмы.
